# Persistence / Performance Review (쿼리 비용)

이 스킬은 **"이 코드가 요청 1건에 DB·Redis 를 몇 번 때리는가"** 만 본다. 트랜잭션 경계·락·커밋
타이밍은 `concurrency-review`, 구조·계약은 `architecture-review` 담당이다.

판정 기준은 "느려 보인다"가 아니라 **비용을 수식으로 쓸 수 있는가**다. 각 지적에는
`요청 1회 → 쿼리 1 + N회 (N = 페이지 크기)` 같은 **크기**가 붙어야 한다. 크기를 못 쓰면 지적하지 않는다.

## 0. 스코프 잡기
1. 오케스트레이터가 준 스코프를 그대로 쓴다. 없으면 `git diff --name-only`(+ staged, 없으면 `main...HEAD`).
2. **엔티티 매핑부터 확인한다.** 서비스 코드만 보고 N+1 을 단정하지 않는다. 같은 BC 안 연관관계
   (`@ManyToOne`, 전부 `LAZY` 가 규칙)와 `@SQLRestriction` 을 엔티티 파일에서 직접 읽는다.
   타 BC 는 ID 참조뿐이므로, 타 BC 데이터의 N+1 은 **QueryApi 반복 호출** 형태로 나타난다.
3. 인덱스는 엔티티의 `@Table(indexes = ...)` 에서 확인한다. 없으면 단정하지 말고 ❓.
4. `docs/*bench*.md`, `docs/*loadtest*.md` 를 확인한다. 이미 측정·튜닝이 끝난 경로면 그 결론과
   어긋나는 제안을 하지 않고, 필요하면 문서를 근거로 인용한다.

## 체크리스트

### A. N+1 · 연관 로딩
- 조회 결과를 루프 돌며 연관 getter 를 부르지 않는가? (`Result.from(entity)` 안의 `entity.getX().getY()` 가 전형)
- QueryService 가 타 BC 정보를 **`getInfos(ids)` 한 번**이 아니라 항목마다 `getInfo(id)` 로 부르지 않는가?
  → 쿼리 수가 페이지 크기에 비례한다. 규칙상 쿼리 수는 **BC 수만큼 고정**이어야 한다.
- 컬렉션 fetch join + 페이징을 같이 쓰지 않는가? (`HHH000104`, 전체를 메모리로 올림) 여러 컬렉션을
  동시에 fetch join 하지 않는가? (카티션 곱)

### B. 쿼리 형태 (QueryDSL)
- `where` 조건이 인덱스를 탈 수 있는가? ❌ 컬럼에 함수 적용, 앞 와일드카드 `LIKE '%x'`, 타입 캐스팅.
- 복합 인덱스 조회가 **선행 컬럼부터** 조건에 들어가는가? 정렬 키가 인덱스와 맞아 filesort 를 피하는가?
- 커서 페이징의 커서 조건이 정렬 키와 일치하는가? (동률 처리용 보조 키 포함)
- 오프셋 페이징의 `count` 쿼리에 불필요한 조인·정렬이 붙지 않았는가?
- 목록·집계에서 엔티티 전체 대신 필요한 컬럼만 projection 하는가?

### C. 반복문 안의 I/O (팬아웃 증폭)
- 루프 안 `save()`/`findById()`/Redis 단건 호출 → `saveAll`, `findAllByIdIn`, `multiGet`/파이프라인 대상.
  채팅·알림 팬아웃은 **인원 수만큼 증폭**되므로 이 축에서 가장 비싼 결함이다.
- IDENTITY 전략에서는 JDBC 배치 insert 가 꺼진다는 점을 고려했는가?

### D. 커넥션·자원 점유
- 트랜잭션 구간에 불필요한 조회·변환·대기가 들어있지 않은가? ("구간이 길다"는 비용만 — 외부 호출 자체는 동시성 축)
- 읽기 전용 조회에 `readOnly = true` 가 빠지지 않았는가? (더티체킹 스냅샷 비용)
- 인스턴스당 pool 15(dev 프로필) 전제에서 이 경로가 커넥션을 오래 쥐면 몇 rps 에서 포화되는지 한 줄 추정.

### E. 캐시 · 소프트 삭제
- 자주 읽히고 거의 안 바뀌는 데이터(구단·경기)를 매번 DB 에서 읽지 않는가? 캐시 제안은
  **무효화 시점**을 함께 쓸 수 있을 때만 한다. 못 쓰면 ❓.
- `@SQLRestriction` 엔티티를 네이티브 쿼리로 읽으면 필터가 빠진다 → 삭제 데이터 노출·count 불일치.

## 리포트 형식
- **확실한 위반만** 보고한다 (오탐 0 목표). 애매하면 "확인 필요" + 확정에 필요한 측정 한 줄.
- 각 항목: `[성능] 파일:라인` · **비용 크기**(쿼리 N회 / 왕복 N회 / 스캔 범위) · 제안 수정.
- 심각도: **🔴** 사용자 수·인원 수·페이지 크기에 비례해 증폭되는 비용 > **🟡** 고정 비용 낭비
  (불필요 조회, readOnly 누락, count 비최적화) > **🟢** 개선 여지.
- 끝에 한 줄 총평. 측정 문서와 대조했으면 그 사실을 적는다.
