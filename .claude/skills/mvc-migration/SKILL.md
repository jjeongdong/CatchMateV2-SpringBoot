# MVC 마이그레이션 오케스트레이터

**실행 모드: 하이브리드.** Phase 2 파일럿은 순차 파이프라인(계획→변환→검증), Phase 3 확산은
컨텍스트 단위 병렬 서브에이전트 위임. 빌드 명령만은 **오케스트레이터가 직렬로 1회** 돌린다.

이 작업은 되돌리기 어렵다. **매 라운드가 커밋 가능한 상태로 끝나야 한다** — 컴파일 통과 +
검증 통과. 중간 상태로 여러 컨텍스트를 벌려놓지 마라.

---

## Phase 0 — 컨텍스트 확인 (먼저 판별하고 시작)

`.claude/mvc-migration-state.json` 을 읽어 지금이 어느 지점인지 판별한다.

| 상황 | 판별 | 동작 |
|---|---|---|
| **최초 실행** | 상태 파일 없음 | Phase 1 부터 전체 |
| **파일럿 진행 중** | `migrated` 가 빈 배열 | Phase 2 |
| **확산 중** | `migrated` 에 1개 이상, 전부는 아님 | Phase 3 (다음 라운드) |
| **재검증만** | "검증만 다시", "재검증" | Phase 4 만 |
| **반려 수정** | 직전 라운드에 미해결 발견 | 같은 converter 재호출 → Phase 4 |
| **완료 정리** | 전 컨텍스트 `migrated` | Phase 5 |
| **상태 조회** | "전환 상태", "어디까지 했지" | 상태 파일 + `dep-graph.py` 요약만 보고하고 종료 |
| **롤백** | "되돌려줘" | `mvc-guardrail-switch` §막혔을 때 참조 |

현재 상태를 한 줄로 사용자에게 보여주고 시작한다:
`전환 {N}/14 완료 [{목록}] · 다음 대상 {ctx} · 순환 {해소됨/미해소}`

## Phase 1 — 준비 (최초 1회)

1. **작업 트리가 깨끗한지 확인한다.** `git status --short` 에 미커밋 변경이 있으면
   먼저 커밋하거나 스태시하라고 알린다. 이 작업의 diff 는 크고, 섞이면 되돌릴 수 없다.
2. **의존 그래프와 순환을 뽑는다:**
   ```bash
   python3 .claude/skills/mvc-migration/scripts/dep-graph.py
   ```
   순환이 있으면 `references/cycle-breaking.md` 를 읽고 **끊는 방법을 사용자와 합의한다.**
   순환 해소는 설계 판단이라 에이전트에 위임하지 않는다. 합의 없이 진행하지 마라.
3. **가드레일을 전환 모드로 둔다** — `mvc-guardrail-switch` 스킬 Step 1.
   이 시점의 동작은 전부 헥사고날과 같으므로 안전하다.
4. **파일럿을 정한다.** 기본은 `club`(13개, 주입 의존 0). 작고 leaf 이면서 QueryDSL·이벤트·
   soft delete 를 안 쓰는 컨텍스트라 규칙을 확정하기 좋다.
   ⚠️ 다만 파일럿이 너무 단순하면 규칙이 덜 검증된다. 파일럿 직후 `game`(19, QueryDSL 있음)을
   두 번째로 넣어 규칙을 한 번 더 두들긴다.

## Phase 2 — 파일럿 (순차. 여기서 규칙을 확정한다)

파일럿의 목적은 컨텍스트 하나를 옮기는 게 아니라 **변환 규칙을 실전에서 확정**하는 것이다.
여기서 발견한 규칙 미비점은 `hexagonal-to-mvc-mapping` 스킬에 반영하고 넘어간다.
그러지 않으면 같은 실수를 13번 반복한다.

```
mvc-migration-planner({ctx})          → 계획서
      ↓ 사용자에게 계획서 §2(잃기 쉬운 것)와 §6(열린 질문)을 보여주고 확인받는다
mvc-converter({ctx}, 계획서)           → 코드 변환
      ↓
[오케스트레이터] ./gradlew compileJava  ← 직렬 1회
      ↓
[오케스트레이터] mvc-guardrail-switch Step 2 로 migrated 에 등록  ← ⚠️ 검증 **전**
      ↓
mvc-invariant-guard({ctx}) ∥ mvc-build-verifier({ctx})   ← 한 메시지에 동시 호출
      ↓
🔴 발견 있으면 → mvc-converter 재호출 (같은 에이전트, 발견 목록 첨부) → 다시 검증
      ↓ 통과
커밋 제안 (사용자가 결정)
```

**계획서 확인을 건너뛰지 마라.** §2 는 "옮기다 잃기 쉬운 것" 목록이고, 여기서 놓친 로직은
컴파일도 테스트도 잡지 못한다. 사용자가 봐야 하는 유일한 지점이다.

**`migrated` 등록은 검증 앞에 온다.** 검증기는 `migrated` 목록을 보고 규칙을 가르므로,
등록 전에 검증하면 이미 MVC 로 옮긴 파일을 헥사고날 규칙으로 검사해 전부 위반으로 잡는다.
등록은 "검증을 통과했다는 표시"가 아니라 **"이제 이 규칙으로 봐 달라는 선언"**이다.
검증이 실패하면 목록에서 이름을 빼면 그만이다 (파일 한 줄).

파일럿이 끝나면 **규칙 반영 회고**를 한다:
- 계획서에 없었는데 변환 중 나온 상황이 있었나? → `hexagonal-to-mvc-mapping` 에 추가
- 검증에서 나온 발견이 규칙으로 예방 가능했나? → 규칙에 추가
- converter 가 헤맨 지점이 있었나? → 에이전트 정의에 반영

## Phase 3 — 확산 (라운드 단위 병렬)

`dep-graph.py` 의 변환 순서를 따른다. **한 라운드에 2~3개**를 넘기지 않는다.
많이 벌리면 컴파일이 깨진 상태가 길어지고 되돌릴 수 없다.

현재 순서 (2026-08-21 기준):

| 라운드 | 컨텍스트 | 비고 |
|---|---|---|
| 1 (파일럿) | `club` | leaf, 13개 |
| 2 | `report`, `game` | leaf. game 은 QueryDSL 검증 |
| 3 | `user`, `auth` | user 는 피의존 10개 — 호출부 정정이 많다 |
| 4 | `notice`, `inquiry` | |
| 5 | `oauth` | |
| 6 | `board`, `bookmark`, `chat`, `enroll` | **순환 4개. 반드시 한 라운드로 묶는다** |
| 7 | `admin`, `notification` | 가장 크고 의존이 많다. 마지막 |

라운드 6 은 하나만 옮기면 나머지 셋이 아직 UseCase 를 노출하고 있어 중간 상태가 컴파일되지
않는다. **planner 를 4개 병렬로 돌리고, converter 도 4개 병렬로 돌린 뒤, 컴파일은 4개가 다
끝난 뒤에 한 번** 돌린다.

### 병렬 호출 규칙

- planner 는 컨텍스트별로 **한 메시지에 동시 호출**한다. 서로 독립적이다.
- converter 도 동시 호출하되, **각자 gradle 을 부르지 않게** 프롬프트에 명시한다.
  병렬 converter 가 각자 gradle 을 부르면 데몬 lock 이 충돌한다.
  (테스트 팀 하네스에서 같은 문제를 겪었다. 같은 해법을 쓴다.)
- 빌드·검증 명령은 **오케스트레이터가 라운드당 1회**.

### converter 프롬프트에 반드시 넣을 것

- 해당 컨텍스트의 계획서 전문
- `hexagonal-to-mvc-mapping` 이 SSOT 라는 지시
- **이미 전환된 컨텍스트 목록** — 이들을 부를 땐 `{Ctx}Service` 를 직접 주입한다
- **아직 전환 안 된 컨텍스트 목록** — 이들의 FetchAdapter 를 만나면 주입 타입·반환 타입만
  고치고 그 컨텍스트를 함께 옮기지 않는다
- `./gradlew` 를 직접 부르지 말라는 지시

## Phase 4 — 검증 (매 라운드 끝)

두 에이전트를 **한 메시지에 동시 호출**한다. 보는 것이 겹치지 않는다.

| 에이전트 | 담당 |
|---|---|
| `mvc-build-verifier` | 컴파일·계층 검사·순환·테스트·컨텍스트 로딩 — **돌아가는가** |
| `mvc-invariant-guard` | 원본과 대조해 런타임 동작 보존 — **같은 일을 하는가** |

**컨텍스트 로딩 테스트 결과를 반드시 확인한다.** 생성자 주입 순환은 컴파일을 통과하고
부팅에서만 터진다. verifier 가 이 단계를 `⏭️` 로 표시했다면 순환 검증이 안 된 것이다.

### 반려 처리

- 🔴 발견 → 같은 `mvc-converter` 를 재호출한다 (컨텍스트를 유지한 채 고치게 한다).
  발견 목록을 그대로 첨부하고, **해당 항목만 고치라고** 지시한다.
- 🟡/⚪ → 사용자에게 보고하고 판단을 받는다. 임의로 고치지 않는다.
- 순환 의존 발견 → **converter 에 넘기지 마라.** 설계 판단이므로
  `references/cycle-breaking.md` 를 근거로 사용자와 합의한다.
- 2회 재호출로도 🔴 이 안 잡히면 멈추고 사용자에게 올린다. 무한 루프에 빠지지 않는다.

### 라운드 종료 조건

전부 만족해야 다음 라운드로 간다:
- [ ] `./gradlew compileJava` 통과
- [ ] `mvc-validate-arch.py --scan` 통과
- [ ] 컨텍스트 로딩 성공 (순환 없음)
- [ ] `mvc-invariant-guard` 🔴 0건
- [ ] `migrated` 에 등록 완료
- [ ] 커밋 (사용자 결정)

테스트 실패는 별도로 다룬다 — `src/test` 27개가 옛 UseCase 를 모킹하고 있어 전환마다 깨진다.
**테스트 수정은 이 하네스의 범위 밖이다.** 깨진 테스트 목록을 모아두고, 라운드가 끝날 때마다
`test-team` 하네스로 넘기라고 사용자에게 알린다.

## Phase 5 — 완료 정리

전 컨텍스트가 `migrated` 에 올라간 뒤에만 한다. `mvc-guardrail-switch` 스킬 Step 4 를 따른다.
헥사고날 자산 삭제는 **되돌리기 어려우므로** 실제 배포로 며칠 굴려본 뒤에 하라고 권한다.

`CLAUDE.md` 의 아키텍처 절 개정도 여기서 한다.

## 에러 핸들링

| 상황 | 처리 |
|---|---|
| 에이전트 무응답/실패 | 1회 재호출. 재실패하면 그 컨텍스트를 이번 라운드에서 빼고 **리포트에 명시**. 조용히 건너뛰지 않는다 |
| 컴파일이 안 잡힘 | 라운드를 **되돌린다** (`git checkout -- src/main/java/.../{ctx}`). 부분 성공 상태로 다음 라운드에 가지 않는다 |
| QueryDSL Q클래스 오류 | `./gradlew clean compileJava` 1회 재시도 |
| 순환이 실제로 터짐 | 즉시 중단. 설계 판단이므로 사용자에게 올린다 |
| planner 와 실제 소스 불일치 | 소스를 따르고 리포트에 적는다. 계획서는 스냅샷이다 |
| 작업 트리에 다른 변경이 섞임 | 진행 전 사용자에게 알린다. diff 가 커서 나중에 분리할 수 없다 |

## 테스트 시나리오

**정상 흐름:** 사용자가 "MVC 로 바꿔줘" → Phase 0 에서 상태 파일 없음 확인 → Phase 1 에서
`dep-graph.py` 로 순환 4개 발견 → `cycle-breaking.md` 근거로 "조립을 `BoardResponseAssembler`
로 올린다" 를 사용자와 합의 → 가드레일 전환 모드 ON → `club` 파일럿 계획서 → 사용자 확인 →
변환 → 컴파일 통과 → 검증 2개 병렬 → 🔴 0건 → `migrated: ["club"]` 등록 → 커밋 제안 →
규칙 회고 후 라운드 2 안내.

**에러 흐름:** 라운드 6(순환 4개)에서 converter 4개가 병렬로 끝난 뒤 컴파일 → `cannot find
symbol: BookmarkInternalQueryUseCase` (board 의 호출부 정정 누락) → verifier 가 `컴파일 — import
누락 / converter` 로 분류 → board converter 재호출, 해당 오류만 첨부 → 재컴파일 통과 →
invariant-guard 가 `🔴 BoardService.createBoard() 의 @Transactional 소실` 보고 → converter
재호출 → 통과 → 4개 동시 등록.
