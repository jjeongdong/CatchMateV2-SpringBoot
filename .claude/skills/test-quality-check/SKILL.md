# Test Quality Check (실행 + 품질 비평)

**통과가 곧 품질이 아니다.** 초록불인데 아무것도 증명하지 않는 테스트는 유지보수 비용만 남기고
리팩터링에 거짓 안전감을 준다. 이 스킬의 판정 기준은 하나다 —
**"이 테스트를 지웠을 때 무엇을 못 잡게 되는가."** 답이 없으면 그 테스트는 값이 없다.

## 0. 실행

대상만 필터해서 돌린다 (전체 `./gradlew test` 는 느리다):
```bash
./gradlew test --tests "com.back.catchmate.{패키지}.{클래스}Test"
./gradlew test --tests "com.back.catchmate.chat.application.service.*"   # 패키지 단위
```
컴파일만 빠르게 보려면 `./gradlew compileTestJava`.

실행 결과는 **통과 N / 실패 M / 스킵 K** 숫자로 기록한다.

## 1. 실패 원인 분류 (섞어서 보고하지 말 것)

| 유형 | 신호 | 책임 |
|---|---|---|
| **컴파일 실패** | `cannot find symbol`, `incompatible types` | 작성자 — import 누락이 대부분 |
| **단언 실패** | `expected: X but was: Y` | 작성자 또는 **진짜 버그** — 아래 참조 |
| **모킹 오류** | `UnnecessaryStubbingException`, `MissingMethodInvocation`, `WrongTypeOfReturnValue` | 작성자 — 스텁이 실제 호출과 안 맞음 |
| **환경 의존** | `@SpringBootTest` 컨텍스트 로딩 실패, DB 커넥션 거부, `local` 프로파일 부재 | **작성 품질 문제 아님** — 구분해서 보고 |

**단언 실패는 두 가지를 구분한다.** 테스트가 틀렸는가, 프로덕션이 틀렸는가.
후자로 보이면 반려하지 말고 **"프로덕션 버그 의심"으로 분리 보고**한다 — 이건 사용자가 판단할 일이다.

## 2. 품질 체크리스트

### A. 무엇도 증명하지 않는 테스트 (가장 흔한 결함)
- **단언이 없다** — `assertThat` 없이 호출만 하고 끝난다. 예외만 안 나면 통과 → 아무것도 못 잡는다.
- **`verify`/`then(...).should()` 만 있고 반환값·상태 단언이 없다** — 호출 여부만 보면 반환 로직이
  통째로 바뀌어도 통과한다. (호출 검증이 목적인 케이스는 정당하니, 계획서에서 의도를 확인할 것)
- **단언이 입력을 그대로 되풀이한다** — 스텁으로 넣은 값을 그대로 단언하면 로직을 안 태운 것이다.

### B. 로직을 우회한 테스트
- **sut 자신을 모킹**했다 → 아무것도 테스트하지 않는다. 즉시 반려.
- **도메인 모델·Command DTO·record 를 모킹**했다 → 진짜 로직이 안 돌았다. 진짜 객체로 만들어야 한다.
- 모킹이 너무 많아 **테스트가 사실상 Mockito 동작을 검증**하고 있다.

### C. 케이스 구성
- **해피패스만 있다** — 계획서의 예외·경계 케이스가 구현되지 않았다.
- **예외 경로에 부수효과 단언이 없다** — 예외는 던지는데 저장·이벤트가 일어났는지 안 본다.
- **`ErrorCode` 를 단언하지 않았다** — `isInstanceOf(BaseException.class)` 만으로는 어떤 에러인지
  못 박지 못한다. 이 앱에서 `ErrorCode` 는 곧 HTTP 응답이다.

### D. 비용·형식
- **불필요한 `@SpringBootTest`** — 서비스 단위 테스트로 증명 가능한데 스프링 컨텍스트를 띄웠다.
  (DB·동시성·실제 SQL 검증이 아니면 반려 대상)
- 통합 테스트가 **자기가 만든 데이터를 정리하지 않는다.**
- `@DisplayName` 이 없거나 "test1" 류다 — 실패 로그만으로 무엇이 깨졌는지 읽혀야 한다.
- JUnit `assertEquals` 를 썼다 (이 프로젝트는 AssertJ 로 통일).
- 기존 테스트 파일과 **네이밍·스타일이 어긋난다** (한글/영문 혼용, given-when-then 블록 부재).

### E. 계획 대비
- 계획서의 케이스 중 **구현되지 않은 것**이 있는가? (writer 가 이유를 밝혔으면 정당한 누락)
- 계획에 **없던 케이스가 추가**됐는가? 나쁜 건 아니지만 이유가 없으면 트리비얼일 수 있다.

## 3. "처음부터 전부 초록"이면 한 번 의심한다
특히 **버그 재현 목적** 테스트는 빨강을 거친 흔적이 있어야 한다. 처음부터 통과했다면
모킹이 실제 로직을 우회했거나 단언이 비어 있을 가능성이 높다. 근거가 있으면 "확인 필요"로 올린다.

## 리포트 형식

```
## 테스트 검증 — {대상} (파일 N개 / 테스트 M개)
실행: 통과 N / 실패 M / 스킵 K   ({필터한 gradle 명령})
판정: 통과(수용) | 수정 필요(반려) | 확인 필요

### 🔴 반려 항목 (수정 없이는 수용 불가)
- [테스트검증] 파일:라인 — 무엇이 문제인가 / **이 테스트가 못 잡는 것** / 어떻게 고칠 것인가

### 🟡 개선 권장
### ❓ 확인 필요 (프로덕션 버그 의심 · 환경 의존 실패)
### 계획 대비 누락
### 수용한 부분
- {잘 쓰인 케이스를 한두 개 짚는다 — 다음 작성의 기준이 된다}

**총평**: 한 줄.
```

## 원칙
- 스타일 취향으로 반려하지 않는다. `write-tests` 에 명시된 규약만 근거로 삼는다.
- 지적은 "품질이 낮다"가 아니라 **"이게 바뀌어도 통과한다"** 형태로 쓴다.
- 환경 의존 실패를 작성자 탓으로 반려하지 않는다.
