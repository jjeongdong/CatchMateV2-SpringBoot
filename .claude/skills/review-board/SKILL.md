# Review Board (리뷰어 팀 오케스트레이터)

**실행 모드: 서브에이전트 병렬 위임 (팬아웃/팬인 + 완전성 비평가).**
리뷰어 4명은 전원 **읽기 전용**(`tools` 에 Edit/Write 없음)이라 구조적으로 코드를 고칠 수 없다.
수정 여부는 **항상 사용자와 메인 Claude 가 결정**한다. 이 스킬은 리포트까지만 만든다.

격리가 목적이다 — diff 전문·파일 전문은 서브에이전트 컨텍스트에서만 돌고, 메인엔 **리포트만** 온다.

---

## Phase 0 — 컨텍스트 확인 (먼저 판별하고 시작)

| 상황 | 판별 | 동작 |
|---|---|---|
| **초기 실행** | 이번 세션에 리뷰 이력 없음 | 아래 Phase 1~3 전체 |
| **부분 재실행** | "보안 축만 다시", "동시성만" | 지목된 축만 호출 → 종합은 **그 축 + 직전 리포트**로 |
| **재리뷰** | "수정했으니 다시" | 스코프를 **다시 계산**해서(수정 후 diff) 전체 재실행. 직전 리포트를 각 리뷰어 프롬프트에 "이전 지적" 으로 첨부해 **해소 여부까지 판정**시킨다 |
| **축 지정 단발** | "성능 관점에서만 봐줘" | 오케스트레이션 없이 **한 축만** 실행 — 아래 기준으로 스킬/에이전트를 고른다 |

**축 단독 실행 시 스킬 vs 에이전트** — 이 둘은 대체재가 아니다. **스킬은 체크리스트(방법)** 이고
**에이전트는 격리된 실행자(누가)** 다. 축 하나만 본다고 항상 스킬인 것이 아니다:
- 스코프가 **파일 몇 개**(변경분 리뷰 등) → 해당 축 **스킬**로 메인이 직접 검토한다. 에이전트를
  띄우는 오버헤드가 이득보다 크다.
- 스코프가 **컨텍스트 전체·수십 개 파일** → 해당 축 **에이전트**를 호출한다. 대량의 파일 읽기가
  메인 컨텍스트를 오염시키는 것이 격리의 이유이고, 그건 축이 하나여도 똑같이 적용된다.
  (에이전트는 어차피 같은 스킬을 SSOT 로 읽으므로 체크리스트는 동일하다.)

리뷰 결과는 파일로 저장하지 않는다 (사용자 선택). 직전 리포트는 대화 컨텍스트의 것을 쓴다.

## Phase 1 — 스코프 확정 (모든 리뷰어가 **동일한** 스코프를 받아야 한다)

1. 범위를 정한다:
   - 기본: `git diff --name-only` + staged. 둘 다 비면 워킹트리 전체 변경.
   - 커밋된 범위 지정 시: `git diff --name-only main...HEAD` 등 사용자가 말한 범위.
   - "{컨텍스트} 통째로": `src/main/java/com/back/catchmate/{ctx}/**/*.java` 전체 +
     `python3 .claude/hooks/arch-audit.py {ctx}` 출력을 **용의자 목록**으로 첨부.
2. `*.java` 만 남긴다. 변경된 Java 가 **0개면 여기서 중단**하고 사용자에게 알린다 (팀을 돌리지 않는다).
3. `./gradlew archCheck` 를 **오케스트레이터가 한 번만** 돌린다. 결과(통과/실패)를 모든 리뷰어
   프롬프트에 넣어 **각자 중복 실행하지 않게** 한다. 실패면 구문 위반부터 고치도록 먼저 보고한다.
4. 스코프 요약 한 줄을 사용자에게 보여준다 (`파일 N개 / 범위 / archCheck 결과`).

**규모 절제:** 기본은 4명이다. 파일이 1~2개이고 성격이 명백하면 (예: DTO 하나 추가) 관련 축만
호출하고 그 사실을 리포트에 적는다. 축을 늘리지 않는다.

## Phase 2 — 팬아웃 (⚠️ 반드시 **한 메시지에 4개 Agent 를 동시 호출**)

4개를 각각 다른 메시지로 부르면 직렬화돼 팀의 이점이 사라진다. 한 번에 묶어 호출한다.

| 축 | `subagent_type` | 담당 |
|---|---|---|
| 아키텍처 | `hexagonal-reviewer` | 정문 목적 분리·이벤트 페이로드 소유권·DTO 격리·네이밍·계약 |
| 동시성 | `concurrency-reviewer` | 트랜잭션 경계·2단계 리스너·프록시 함정·Redis 팬아웃·락·STOMP 세션 |
| 성능 | `persistence-perf-reviewer` | N+1·쿼리 형태·페이징·루프 내 I/O·커넥션 점유 |
| 보안 | `auth-security-reviewer` | 인증 경계·STOMP 구독/전송 인가·IDOR·노출·시크릿 |

각 프롬프트에 **똑같이** 넣을 것:
- 리뷰 스코프 (파일 목록 전문, diff 기준 범위)
- `./gradlew archCheck` 결과 (이미 실행됨 — 다시 돌리지 말 것)
- 재리뷰면 "이전 지적" 목록과 "해소 여부도 판정하라"는 지시
- 반환 규칙: **리포트만**, 축 태그(`[아키텍처]`/`[동시성]`/`[성능]`/`[보안]`) 필수, 오탐 0 우선,
  해당 축과 무관하면 "검토 대상 없음"으로 즉시 반환

**네 개의 완료 알림이 모두 도착하기 전에 Phase 3 으로 넘어가지 않는다.** 아직 안 온 리뷰어의
결과를 추측해서 쓰지 않는다 — 사용자가 중간에 물으면 "아직 실행 중"이라고 답한다.

---

## Phase 3 — 팬인 (종합·교차 검증)

`review-synthesizer` 를 **1회** 호출한다. 프롬프트에 넣을 것:
- Phase 1 의 스코프 요약 + `archCheck` 결과
- **리뷰어 4명의 리포트 전문** (요약하지 말고 그대로 전달 — 요약하면 교차 검증할 근거가 사라진다)
- 실패·미실행·"검토 대상 없음" 인 축이 있으면 그 사실

종합 에이전트는 중복 병합 → 🔴 교차 검증(코드 직접 확인 후 확정/기각) → 상충 조정 →
사각지대 점검 순으로 처리하고 정해진 형식의 리포트 1장을 돌려준다.

**메인 Claude 는 종합 리포트를 그대로 사용자에게 제시한다.** 리뷰어 4명의 원본 리포트를 다시
나열하지 않는다 (그러면 종합의 의미가 없다). 사용자가 "원본도 보여줘"라고 하면 그때 보여준다.

리포트를 낸 뒤에는 **수정을 자동으로 시작하지 않는다.** "이 중 무엇부터 고칠까요?"로 끝낸다.

## 데이터 흐름

```
[사용자] "리뷰 팀 돌려줘"
   ↓
[오케스트레이터] 스코프 확정 + archCheck 1회
   ↓ (한 메시지, 병렬)
[hexagonal] [concurrency] [persistence-perf] [auth-security]   ← 전원 읽기 전용
   ↓ 각자 리포트 (축 태그 포함)
[review-synthesizer] 중복 병합 · 🔴 교차 검증 · 상충 조정 · 사각지대
   ↓ 리포트 1장
[메인] 사용자에게 제시 → 수정 여부는 사용자 결정
```

## 에러 핸들링

| 상황 | 대응 |
|---|---|
| 리뷰어 1명 실패 | 1회 재시도. 재실패면 **그 축 없이 진행**하되 종합 프롬프트에 "이 축 미실행" 명시 → 리포트 상단에 노출 (침묵 누락 금지) |
| 리뷰어 2명 이상 실패 | 종합하지 않고 사용자에게 상황 보고 후 지시를 받는다 |
| `archCheck` 실패 | 구문 위반이 이미 있다는 뜻 → 먼저 사용자에게 알리고, 그대로 진행할지 확인 |
| 변경 Java 0개 | 팀을 돌리지 않고 "리뷰할 변경 없음" 보고 |
| 축끼리 상충하는 제안 | 종합 에이전트가 불변 규칙(CLAUDE.md '절대 변경 금지' 3항목) 기준으로 판정. 불변 규칙을 건드리는 제안은 무조건 기각 |
| 종합 에이전트가 🔴 를 전부 기각 | 정상이다. 기각 사유와 함께 "확정 위반 없음"으로 보고한다 |

## 테스트 시나리오

**정상 흐름** — 채팅 관련 파일 8개를 수정한 뒤 "리뷰 팀 돌려줘":
Phase 1 이 8개 파일 + archCheck 통과를 확정 → 4명 동시 실행 → 각자 축 태그 리포트 반환 →
종합이 중복 2건 병합, 🔴 1건은 코드 확인 후 기각, 나머지로 리포트 1장 → 사용자 제시, 수정은 대기.

**에러 흐름** — 성능 리뷰어가 실패:
1회 재시도 후에도 실패 → 나머지 3명 결과로 종합하되, 리포트 상단에 "성능 축 미실행 — 이 리포트는
쿼리 비용을 검토하지 않았다"를 명시. 사용자가 그 축만 재실행할 수 있게 안내.
