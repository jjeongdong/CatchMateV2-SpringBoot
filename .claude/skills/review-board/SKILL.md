# Review Board (리뷰 서브에이전트 오케스트레이터)

**실행 모드: 서브에이전트 위임 (팬아웃/팬인 + 완전성 점검).**
리뷰 관점 4개는 사전에 정해져 있고 서로 통신할 필요가 없으며 결과만 필요하다 — 그래서 단발 서브에이전트를
한 메시지에서 병렬 호출한다. 리뷰어는 전원 읽기 전용(`tools` 에 Edit/Write 없음)이라 구조적으로 코드를
고칠 수 없다. **수정 여부는 항상 사용자가 결정한다.** 이 스킬은 리포트까지만 만든다.

격리가 목적이다 — diff·파일 전문은 서브에이전트 컨텍스트에서만 돌고, 메인에는 리포트만 온다.

---

## Phase 0 — 컨텍스트 확인

| 상황 | 판별 | 동작 |
|---|---|---|
| **초기 실행** | 이번 세션에 리뷰 이력 없음 | Phase 1~3 전체 |
| **부분 재실행** | "보안 축만 다시", "동시성만" | 지목된 관점만 호출 → 종합은 **그 관점 + 직전 리포트**로 |
| **재리뷰** | "수정했으니 다시" | 스코프를 **다시 계산**해 전체 재실행. 직전 종합 리포트를 각 리뷰어 프롬프트에 "이전 지적"으로 넣어 **해소 여부까지 판정**시킨다 |
| **관점 하나만** | "성능 관점에서만 봐줘" | 오케스트레이션 없이 한 관점만 — 아래 기준으로 스킬/에이전트 선택 |

**관점 하나만 볼 때 스킬 vs 에이전트** — 스킬은 체크리스트(방법), 에이전트는 격리된 실행자(누가)다.
- 스코프가 **파일 몇 개** → 해당 관점 **스킬**로 메인이 직접 검토한다. 에이전트를 띄우는 비용이 더 크다.
- 스코프가 **BC 전체·수십 개 파일** → 해당 관점 **에이전트**를 호출한다. 대량 파일 읽기가 메인 컨텍스트를
  오염시키는 게 격리의 이유이고, 관점이 하나여도 똑같다.

리뷰 결과는 파일로 저장하지 않는다. 직전 리포트는 대화 컨텍스트의 것을 쓴다.

---

## Phase 1 — 스코프 확정 (모든 리뷰어가 **같은** 스코프를 받는다)

1. 범위를 정한다:
   - 기본: `git diff --name-only` + `git diff --name-only --staged`. 둘 다 비고 현재 브랜치가 `main` 이 아니면
     `git diff --name-only main...HEAD`(브랜치 전체 변경).
   - 사용자가 범위를 지정하면 그 범위.
   - "{bc} 통째로": `src/main/java/com/back/catchmate/{bc}/**/*.java` 전체.
2. `src/main/**/*.java` 만 남긴다 (테스트 코드는 리뷰 대상이 아니다). **0개면 여기서 중단**하고 알린다.
3. 아키텍처 테스트를 **오케스트레이터가 한 번만** 돌린다:
   `./gradlew test --tests 'com.back.catchmate.architecture.*'`
   결과를 모든 리뷰어 프롬프트에 넣어 **각자 Gradle 을 돌리지 않게** 한다 (병렬 실행 시 데몬 lock 충돌).
   실패하면 구문 위반이 이미 있다는 뜻이므로 사용자에게 먼저 알리고 계속할지 묻는다.
4. 스코프 요약 한 줄을 사용자에게 보여준다 (`파일 N개 / 범위 / 아키텍처 테스트 결과`).

**규모 절제:** 기본은 4명이다. 파일이 1~2개이고 성격이 명백하면(예: Request DTO 하나 추가) 관련 관점만
호출하고 그 사실을 리포트에 적는다.

## Phase 2 — 팬아웃 (⚠️ 반드시 **한 메시지에 Agent 4개를 동시 호출**)

따로따로 부르면 직렬화되어 병렬의 이점이 사라진다.

| 관점 | `subagent_type` | 담당 |
|---|---|---|
| 아키텍처 | `architecture-reviewer` | 규칙 위치 · BC 경계 · 이벤트 계약 · DTO 흐름 · 에러 설계 · API 계약 |
| 동시성 | `concurrency-reviewer` | 트랜잭션 경계 · 리스너 phase · Outbox · 프록시 함정 · Redis · 락 · 스케줄러 · STOMP 세션 |
| 성능 | `persistence-perf-reviewer` | N+1 · QueryApi 반복 호출 · 쿼리 형태 · 페이징 · 루프 내 I/O · 커넥션 점유 |
| 보안 | `auth-security-reviewer` | 인증 경계 · STOMP 인가 · IDOR · 관리자 권한 · 노출 · 시크릿 |

각 프롬프트에 **똑같이** 넣을 것:
- 리뷰 스코프 (파일 목록 전문, 기준 범위)
- 아키텍처 테스트 결과 ("이미 실행됨 — Gradle 을 돌리지 말 것")
- 재리뷰면 "이전 지적" 목록과 "해소 여부도 판정하라"는 지시
- 반환 규칙: 리포트만, 관점 태그 필수, 오탐 0 우선, 해당 관점과 무관하면 "검토 대상 없음"으로 즉시 반환

**4개 완료 알림이 모두 오기 전에 Phase 3 으로 넘어가지 않는다.** 아직 안 온 결과를 추측해서 쓰지 않는다.
사용자가 중간에 물으면 "아직 실행 중"이라고 답한다.

---

## Phase 3 — 팬인 (종합·교차 검증)

`review-synthesizer` 를 **1회** 호출한다. 프롬프트에 넣을 것:
- Phase 1 스코프 요약 + 아키텍처 테스트 결과
- **리뷰어 리포트 전문** (요약하지 않는다 — 요약하면 교차 검증의 근거가 사라진다)
- 실패·미실행·"검토 대상 없음"인 관점

메인은 **종합 리포트를 그대로** 사용자에게 보여준다. 원본 4개를 다시 나열하지 않는다 (요청하면 그때 보여준다).
리포트를 낸 뒤 **수정을 자동으로 시작하지 않는다.** "이 중 무엇부터 고칠까요?"로 끝낸다.

## 데이터 흐름

```
[사용자] "리뷰 팀 돌려줘"
   ↓
[오케스트레이터] 스코프 확정 + 아키텍처 테스트 1회
   ↓ (한 메시지, 병렬)
[architecture] [concurrency] [persistence-perf] [auth-security]   ← 전원 읽기 전용
   ↓ 관점 태그가 붙은 리포트
[review-synthesizer] 중복 병합 · 🔴 교차 검증 · 상충 조정 · 사각지대
   ↓ 리포트 1장
[메인] 사용자에게 제시 → 수정 여부는 사용자 결정
```

## 에러 핸들링

| 상황 | 대응 |
|---|---|
| 리뷰어 1명 실패 | 1회 재시도. 재실패면 그 관점 없이 진행하되 종합 프롬프트에 "이 관점 미실행" 명시 → 리포트 상단에 노출 (조용히 누락 금지) |
| 리뷰어 2명 이상 실패 | 종합하지 않고 사용자에게 상황 보고 후 지시를 받는다 |
| 아키텍처 테스트 실패 | 사용자에게 먼저 알리고 계속할지 확인한다 |
| 아키텍처 테스트 실행 불가 (Gradle 오류) | "미실행"으로 표시하고 진행한다. 리뷰어에게도 미실행이라고 알린다 |
| 변경 Java 0개 | 팀을 돌리지 않고 "리뷰할 변경 없음" 보고 |
| 관점끼리 상충 | 종합 에이전트가 `CLAUDE.md` 절대 규칙과 Outbox 구조 기준으로 판정. 절대 규칙을 깨는 제안은 기각 |
| 종합이 🔴 를 전부 기각 | 정상이다. 기각 사유와 함께 "확정 위반 없음"으로 보고 |

## 테스트 시나리오

**정상 흐름** — chat 의 Service·리스너 6개를 수정한 브랜치에서 "리뷰 팀 돌려줘":
Phase 1 이 `main...HEAD` 로 6개 파일 + 아키텍처 테스트 통과를 확정 → 4명 동시 실행 → 각자 태그 리포트 반환 →
종합이 중복 2건 병합, 🔴 1건은 코드 확인 후 기각, 나머지로 리포트 1장 → 사용자 제시, 수정은 대기.

**에러 흐름** — 성능 리뷰어 실패:
1회 재시도 후에도 실패 → 나머지 3명 결과로 종합하되 리포트 상단에 "성능 관점 미실행 — 쿼리 비용을 검토하지
않았다"를 적고, 그 관점만 재실행할 수 있다고 안내한다.

**재리뷰 흐름** — 🔴 2건을 고친 뒤 "수정했으니 재리뷰":
스코프 재계산 → 직전 종합 리포트를 "이전 지적"으로 첨부해 4명 재실행 → 종합 리포트 첫 섹션에 이전 지적별
해소 여부가 나온다.
