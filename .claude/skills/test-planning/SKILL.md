# Test Planning (무엇을 테스트할 것인가)

작성 규약은 `write-tests` 가 SSOT 다. 이 스킬은 그 앞단 — **케이스 도출**만 다룬다.

판정 기준은 하나다: **"이 테스트를 지웠을 때 어떤 회귀를 놓치게 되는가."** 답을 한 줄로 못 쓰면
그 케이스는 만들지 않는다. 커버리지 숫자를 위한 테스트는 유지보수 비용만 남긴다.

## 0. 먼저 확인할 것
1. 대상 클래스의 **레이어**를 판정한다 (`write-tests` 의 레이어 판단표 사용 — 여기 복제하지 않는다).
2. `src/test/java` 에서 **같은 대상의 기존 테스트**를 찾는다. 이미 커버된 케이스는 제안하지 않고,
   기존 파일의 네이밍·스타일을 계획서에 적어 writer 가 일관성을 지키게 한다.
3. 대상 메서드 **본문을 읽는다.** 시그니처만 보고 케이스를 지어내지 않는다.

## 케이스 도출법

### A. 분기마다 하나 — 가장 기본
메서드 본문의 `if` / early return / `throw` / `switch` / 삼항 **각각에 케이스 하나**를 배정한다.
분기를 지나가지 않는 테스트는 그 분기의 회귀를 못 잡는다.

특히 이 코드베이스에서 자주 나오는 분기:
- **가드 절** — 권한 없음(`FORBIDDEN_ACCESS`), 존재하지 않음(`NOT_FOUND`), 중복 상태
  (`ALREADY_ENROLL_ACCEPTED`), 재진입 불가(`CHATROOM_REENTRY_NOT_ALLOWED`)
- **Optional 분기** — `orElseThrow` 의 양쪽(값 있음 / 비어 있음)
- **상태 전이 가드** — 이미 전이된 상태에서 다시 전이 시도

### B. 경계값 — 버그가 실제로 사는 곳
- 컬렉션: 빈 리스트 / 1건 / 여러 건 (0건과 1건은 다른 코드 경로인 경우가 많다)
- 숫자: 0, 음수, 최대 재시도 횟수 **직전과 초과**
- 시간: TTL 만료 전/후, 스케줄 주기 경계
- null / 빈 문자열이 **허용되는지 아닌지**가 코드에 드러나 있으면 그 계약을 못 박는다

### C. 예외 경로의 **부수효과 없음** 단언
이 코드베이스에서 가장 값진 케이스다. 가드에 걸린 요청은 아무것도 남기면 안 된다:
- `then(repository).should(never()).save(any())`
- `then(eventPublisher).shouldHaveNoInteractions()`
- Redis/외부 어댑터가 호출되지 않았음

예외를 던지는지만 보고 부수효과를 안 보면, "예외는 던지지만 이미 저장은 된" 버그를 놓친다.

### D. 상태 전이 (도메인 모델)
`Outbox` 처럼 상태를 가진 도메인은 **전이 표**를 만들어 케이스를 뽑는다:
정상 전이 / 불가능한 전이 / 전이 시 함께 바뀌는 필드(재시도 횟수·에러 메시지·타임스탬프).
반환값이 없어도 **호출 후 객체 상태 단언**이 결과다.

### E. 이벤트·비동기 경계
- 이벤트가 **발행되는지**와 **페이로드 내용**을 함께 단언한다 (`ArgumentCaptor`).
  발행 여부만 보면 잘못된 값이 실려도 통과한다.
- 커밋 전/후 분리(2단계 리스너)는 단위 테스트로 순서를 증명할 수 없다. 그건 계획에서 제외하고
  **각 리스너 메서드가 무엇을 호출하는지**만 단위로 확인한다.

### F. cross-context
자기 **FetchPort 를 모킹**한다 (상대 UseCase 를 직접 모킹하지 않는다). 케이스는 두 개가 기본:
포트가 정상 응답할 때 / 포트가 예외를 던지거나 빈 값을 줄 때 서비스가 어떻게 행동하는가.

## 만들지 말아야 할 케이스
- getter/setter, 순수 DTO 변환만 하는 record
- 프레임워크 동작 검증 (JPA 가 저장하는지, Jackson 이 직렬화하는지)
- 얇은 위임 어댑터 (`FetchAdapter` 가 UseCase 를 그대로 호출) — 위임 한 줄에 테스트를 붙이면
  리팩터링마다 깨지기만 한다
- 모킹이 로직 전부를 대체해 **사실상 Mockito 를 테스트하는** 케이스

대상이 위에 해당하면 **"테스트 불필요"로 반환한다.** 이것도 유효한 결론이다.

## 감사 모드 (테스트 공백 진단)

"{컨텍스트} 테스트 채워줘" 처럼 대상이 지정되지 않은 경우.

1. 대상 컨텍스트의 `src/main` 클래스 목록과 `src/test` 를 대조해 **테스트 없는 클래스**를 뽑는다.
2. 아래 **위험도**로 정렬한다 (높은 것부터):

| 순위 | 대상 | 이유 |
|---|---|---|
| 1 | 상태 전이를 가진 **도메인 모델** | 전이 규칙이 깨지면 데이터가 오염되고, 모킹 없이 싸게 검증된다 |
| 2 | **가드(권한·중복·상태)가 있는 Service** | 뚫리면 곧 보안·정합성 사고 |
| 3 | 분기가 있는 **Reader/Executor** | 조회 조건 실수가 조용히 통과한다 |
| 4 | 이벤트를 **발행**하는 Service | 페이로드 계약이 구독자에 영향 |
| 5 | 그 외 Command/Query Service | |
| — | 얇은 위임 어댑터·DTO·Config | **대상 아님** |

3. 상위 10개까지만 제시하고 나머지는 건수만 알린다. 한 번에 다 채우려 하지 않는다.

## 산출물 형식 (writer 가 그대로 구현할 수 있어야 한다)

```
## 테스트 계획 — {대상 FQCN}
레이어: {도메인 단위 | 서비스 단위 | 통합} · 기존 테스트: {있음(파일명, 스타일) | 없음}
모킹 대상: {out 포트 목록} · sut: {클래스명}

### 케이스
1. `{메서드명 또는 한글 서술형}` — @DisplayName: "{~하면 ~한다}"
   - 대상 메서드: {method(args)}
   - given: {스텁할 포트와 반환값 — 구체적으로}
   - when: {호출}
   - then: {반환값 / 예외 ErrorCode / 객체 상태}
   - 부수효과 단언: {never().save() 등, 없으면 "없음"}
   - **왜 필요한가**: {이 테스트가 없으면 놓치는 회귀 한 줄}
2. ...

### 제외한 것
- {대상}: {왜 테스트하지 않는가}
```
