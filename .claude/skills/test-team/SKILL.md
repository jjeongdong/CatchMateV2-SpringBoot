# Test Team (계획 → 작성 → 검증 오케스트레이터)

**실행 모드: 서브에이전트 위임 (생성-검증 루프).**
리뷰어 팀과 달리 이 팀은 **쓰기가 개입**한다. 그래서 경계가 더 중요하다.

## ⚠️ 팀 전체 가드레일 (모든 Phase 에 적용)

- **`src/test/java/**` 만 수정한다.** `src/main`·빌드 스크립트·`application*.yml` 은 건드리지 않는다.
  테스트를 통과시키려고 프로덕션 코드를 고치는 것은 금지 — 진짜 버그로 보이면 **보고하고 멈춘다.**
- **단언을 지워 통과시키지 않는다.** 통과율이 아니라 "무엇을 증명했는가"가 산출물이다.
- CLAUDE.md '절대 변경 금지' 3패턴은 테스트 편의로도 건드리지 않는다.
- 작업 종료 시 `Stop` 훅이 빌드를 검증한다. **컴파일이 깨진 상태로 끝내지 않는다.**

---

## Phase 0 — 컨텍스트 확인

| 상황 | 판별 | 동작 |
|---|---|---|
| **초기 실행** | 이번 세션에 계획 없음 | Phase 1~5 전체 |
| **계획 이어받기** | "아까 계획 나머지도", "2번부터" | 계획 재수립 없이 **Phase 3 부터** (기존 계획서 사용) |
| **반려 수정** | "반려된 것 고쳐줘" | `test-writer` 에 검증 리포트를 넘겨 **Phase 3→4 만** 반복 |
| **검증만** | "돌려보고 봐줘", "이 테스트 제대로 된 거야" | `test-verifier` 단독 호출 (Phase 4 만) |
| **단발** | 클래스 1개에 테스트 2~3개 | 오케스트레이션 없이 `write-tests` 스킬로 메인이 직접 작성 |

중간 산출물은 파일로 저장하지 않는다. 계획서·검증 리포트는 대화 컨텍스트의 것을 쓴다.

---

## Phase 1 — 스코프 확정

1. 모드를 판별한다:
   - **지정 대상 모드** — 사용자가 클래스/서비스를 지목했다. 그대로 스코프.
   - **감사 모드** — "{컨텍스트} 테스트 채워줘". `test-planner` 가 테스트 없는 클래스를 찾아
     위험도 순으로 정렬한다 (상위 10개까지).
   - **변경분 모드** — "방금 만든 것 테스트". `git diff --name-only` 로 바뀐 `*.java` 를 스코프.
2. 스코프 요약을 사용자에게 한 줄 보여준다.
3. **규모 절제** — 한 번에 5개 클래스를 넘기지 않는다. 감사 모드에서 대상이 많으면 상위 우선순위
   3~5개만 이번 라운드로 잡고 나머지는 다음 라운드로 미룬다. 한꺼번에 다 채우려 하지 않는다.

---

## Phase 2 — 계획 (`test-planner`)

`test-planner` 를 호출한다. 대상이 **서로 다른 컨텍스트**로 나뉘면 컨텍스트별 병렬 호출도 좋다
(같은 컨텍스트를 쪼개면 중복 케이스가 나오니 나누지 않는다).

프롬프트에 넣을 것: 대상 FQCN 목록, 모드(지정/감사/변경분), 기존 테스트 유무(알고 있으면).

계획서를 받으면 **사용자에게 보여주고 진행 여부를 확인한다.** 케이스가 많거나(15개 초과) 대상이
"테스트 불필요"로 판정됐으면 특히 그렇다. 사용자가 케이스를 덜어낼 기회를 준다.

---

## Phase 3 — 작성 (`test-writer`)

`test-writer` 를 호출한다. 프롬프트에 넣을 것:
- **계획서 전문** (요약하지 말 것 — 요약하면 given 스텁 같은 구체가 사라져 writer 가 추측하게 된다)
- 가드레일 재확인: `src/test` 만, 프로덕션 수정 금지, 단언 약화 금지
- 반려 수정이면 **검증 리포트의 지적 항목**

대상 클래스가 4개 이상이면 클래스 그룹별로 나눠 **병렬 호출**해도 된다 (각자 다른 테스트 파일을
쓰므로 파일 충돌은 없다). 3개 이하면 1명으로 충분하다.

### 빌드 명령은 오케스트레이터가 직렬로 1회만 실행한다

gradle 데몬은 프로젝트 단위 lock 을 잡는다. 여러 writer 가 동시에 `./gradlew` 를 부르면 lock 대기·
타임아웃으로 **작성 품질과 무관한 실패**가 난다. 이건 gradle 고유 문제가 아니라 **공유 자원을 잡는
명령의 일반 원칙**이다 (빌드·마이그레이션·인덱싱·포트 점유 등 — 병렬 에이전트에게 맡기지 않는다).

- **writer 1명일 때** — writer 가 직접 `./gradlew compileTestJava` 까지 통과시킨 뒤 반환한다.
- **writer 2명 이상일 때** — 프롬프트에 **"`./gradlew` 를 실행하지 말 것"** 을 명시하고, 대신
  `write-tests` 의 import 목록 대조로 오류를 예방하라고 지시한다. 전원 완료 후 오케스트레이터가
  `./gradlew compileTestJava` 를 **1회** 실행하고, 오류가 나면 **그 파일을 작성한 writer 에게만**
  오류 전문을 넘겨 고치게 한다 (다른 writer 를 부르지 않는다).

---

## Phase 4 — 검증 (`test-verifier`)

`test-verifier` 를 호출한다. 프롬프트에 넣을 것:
- 작성된 테스트 파일 목록
- **계획서 전문** (누락 판정 기준)
- writer 의 보고 (미구현 케이스·프로덕션 버그 의심)

판정에 따라:
- **통과(수용)** → Phase 5
- **수정 필요(반려)** → Phase 3 으로 돌아가 `test-writer` 에게 지적을 넘긴다.
  **루프는 최대 2회.** 2회 후에도 반려면 멈추고 남은 지적을 사용자에게 보고한다
  (무한 루프로 토큰을 태우지 않는다).
- **확인 필요(프로덕션 버그 의심)** → 루프를 돌리지 말고 **즉시 사용자에게 판단을 요청**한다.
  프로덕션 수정은 이 팀의 권한 밖이다.

---

## Phase 5 — 보고

메인 Claude 가 사용자에게 정리해 전달한다:
- 작성된 파일 경로와 테스트 수, 실행 결과(통과/실패/스킵)
- 검증에서 **반려됐다가 고친 항목**이 있으면 무엇이었는지 (이게 이 팀의 값이다)
- 계획 대비 **누락된 케이스**와 이유
- 프로덕션 버그 의심이 있으면 별도로 강조
- 감사 모드면 **다음 라운드 후보** (이번에 못 채운 우선순위 목록)

수정 제안을 자동으로 실행하지 않는다. "다음 라운드 갈까요?"로 끝낸다.

## 데이터 흐름

```
[사용자] "chat 컨텍스트 테스트 채워줘"
   ↓
[오케스트레이터] 모드 판별 + 스코프 (최대 5개 클래스)
   ↓
[test-planner] 케이스 목록  ──→ 사용자 확인
   ↓ 계획서 전문
[test-writer] src/test 작성 + compileTestJava
   ↓ 파일 목록 + 미구현 보고
[test-verifier] 실행 + 품질 비평 ──반려──┐
   ↓ 수용                                │ (최대 2회)
[메인] 사용자 보고 ←──────────────────────┘
```

## 에러 핸들링

| 상황 | 대응 |
|---|---|
| planner 가 "테스트 불필요" 판정 | 억지로 작성시키지 않는다. 이유와 함께 사용자에게 보고하고 종료 |
| writer 가 컴파일을 못 맞춤 | 1회 재시도. 재실패면 작성된 파일을 남긴 채 보고 (**컴파일 깨진 채 종료 금지** — 고칠 수 없으면 해당 파일 삭제를 사용자에게 제안) |
| verifier 가 환경 의존 실패 보고 | 작성 품질 문제가 아니다. 반려 루프를 돌리지 말고 그대로 사용자에게 전달 |
| 프로덕션 버그 의심 | 루프 중단 → 사용자 판단 요청. 실패하는 테스트를 남길지도 사용자가 결정 |
| 2회 반려 후에도 미해결 | 멈추고 남은 지적을 그대로 보고. 부분 성공도 성공으로 보고하되 무엇이 남았는지 명시 |
| 감사 모드에서 대상 과다 | 상위 3~5개만 이번 라운드. 나머지는 건수만 알림 |

## 테스트 시나리오

**정상 흐름** — "ChatRoomService 테스트 짜줘":
planner 가 레이어(서비스 단위)·모킹 범위·케이스 7개(정상 2 / 가드 3 / 경계 2) 산출 → 사용자 확인 →
writer 가 파일 1개 작성 + compileTestJava 통과 → verifier 실행: 통과 6 / 실패 1, 그리고 "가드 케이스에
`never().save()` 단언 없음" 반려 → writer 수정 → 재검증 수용 → 보고.

**에러 흐름** — 단언 실패가 프로덕션 버그로 보이는 경우:
verifier 가 "테스트는 맞고 구현이 틀린 것으로 보임"으로 분류 → 루프 중단 → 메인이 사용자에게
"이건 테스트 문제가 아니라 구현 결함으로 보입니다. 고칠까요, 테스트를 보류할까요?" 확인 요청.
